# 第 27 章　部署形态：Lite、标准版与可替换基础设施

[返回全书目录](../README.md) · [上一篇：多租户、RBAC 与 AI 特有的安全边界](05-multi-tenant-rbac-ai-security-boundary.md)

## 本章要解决的问题

把一个 AI 应用放进容器，并不等于完成了部署设计。真正的问题是：同一套业务能力在个人电脑、单机私有化环境和多副本集群中，哪些状态可以留在进程内，哪些必须变成共享且可恢复的基础设施？

WeKnora 给出了两种有意不同的答案：

- **Lite**：单进程、单空间、本机优先；用 SQLite、内存流和进程内任务执行器降低安装成本；
- **标准版**：把数据库、队列/流、文档解析、文件存储和可选检索/图谱服务拆开，以支持协作、持久化和扩展；
- **Kubernetes/Helm**：不是把 Compose 文件“翻译成 YAML”，而是把副本数、网络入口、Secret、卷和升级策略变成可声明的运维契约。

本章不教某一条安装命令，而是建立选择部署形态和判断“能否横向扩容”的方法。

## 先从状态，而不是机器数量开始

传统 Web 服务常被概括为“应用无状态，数据库有状态”。AI 应用更复杂，因为状态散落在更多位置：

| 状态 | 典型内容 | 多副本时的要求 |
| --- | --- | --- |
| 业务事实 | 用户、空间、知识库、消息、权限 | 所有实例读到同一份且支持迁移 |
| 原始文件 | 上传文件、解析中间产物、图片 | 所有处理者能访问同一对象 |
| 检索索引 | 向量、关键词索引、Chunk 元数据 | 与业务记录保持身份和删除语义一致 |
| 异步工作 | 待解析、重试、延迟同步、死信 | 可领取、可确认、崩溃后可恢复 |
| 流式会话 | token/event 缓冲、断线回放位置 | 浏览器可以落到另一实例仍能续接 |
| 配置与密钥 | 模型、存储、JWT、外部连接器凭据 | 可审计、可轮换，不能随镜像漂移 |

因此“再加两个 App Pod”并不是容量操作，而是一次状态架构审计。只要其中一类状态仍只存在某个进程或节点本地，负载均衡就会暴露随机故障：上传后另一实例找不到文件、重连后没有事件、任务被分配却无人继续执行。

### 手工推演：为什么两个副本反而让问题变多

设 App-A 与 App-B 都挂在负载均衡器后，但上传文件仍写各自节点的本地目录。用户把 PDF 上传到 A，数据库记录已经创建；随后解析任务或下载请求恰好落到 B，B 根据同一条数据库记录寻找文件，却找不到本地路径。HTTP、数据库与权限看起来都正常，只有“状态的可见范围”错了。

同样的推演适用于流式问答：若 `M1` 的事件缓冲留在 A 内存，浏览器重连落到 B 时没有事件可回放。解决它不是在负载均衡器上赌粘性会话，而是把需要跨副本恢复的文件、事件和待执行工作放到共享且可恢复的位置；粘性只能减少概率，不能定义可靠性语义。

## Lite：把边界收回单一进程

[`docs/LITE.md`](../../docs/LITE.md) 把 Lite 定位为本地、低资源、零外部依赖的使用形态。它不是没有持久化，而是将需要协调的范围收缩到一台机器、一个进程和一个空间。

```text
浏览器 / 桌面壳
       │ localhost
       ▼
┌─────────────────────────────────┐
│ WeKnora Lite 进程               │
│  HTTP API · SQLite · 本地文件    │
│  内存 Stream · 进程内 Task       │
└─────────────────────────────────┘
       │
       └── 模型与外部数据源（按配置访问）
```

这条路径的价值是缩短“下载到第一次问答”的距离：不要求用户另行安装 PostgreSQL、Redis 或消息队列，数据默认保留在本机，默认网络暴露也更小。桌面入口 [`cmd/desktop/main.go`](../../cmd/desktop/main.go) 会把 `handler.Edition` 固定为 `lite`；当没有 `REDIS_ADDR` 时，它还会将错误继承来的 Redis Stream 设置改为 memory，避免桌面程序意外拨号到 `localhost:6379`。

### Lite 省掉了什么，又保留了什么

“零依赖”不意味着异步工作消失。[`internal/router/sync_task.go`](../../internal/router/sync_task.go) 的 `SyncTaskExecutor` 仍注册文档处理、图片多模态、数据源同步、Wiki 和长期记忆等任务处理器；区别是 `Enqueue` 在进程内启动 goroutine，并尽力保留延迟、重试、超时、Deadline 和最终失败回调的语义。

这是一种很好的工程折中：调用方依旧面向 `TaskEnqueuer`，业务代码不用到处写 `if lite`；但它不能制造分布式队列本来具备的能力。

| 维度 | Lite 进程内执行 | Redis/Worker 执行 |
| --- | --- | --- |
| 排队与领取 | 当前进程直接调度 | 独立 Worker 可竞争领取 |
| 重启后的待执行任务 | 内存中的工作可能丢失，需靠业务状态恢复/标失败 | 队列与重试记录可继续被 Worker 消费 |
| 多实例 | 不适用；内存互不可见 | 需配合租约、幂等和共享队列 |
| 运维成本 | 极低 | 需监控 Redis、队列深度、Worker 和死信 |
| 适用目标 | 个人、本机试用、小规模单机 | 协作、长任务、可靠恢复和水平扩展 |

`SyncTaskExecutor` 并非真的“同步阻塞 HTTP 请求”：它创建 goroutine 后立即返回。名称中的 sync 指的是**没有外部持久队列、在本进程执行**。这也解释了其失败模式：进程退出时，goroutine、内存 Stream 和尚未来得及写出的协调状态都不会自动迁移给另一实例。

Lite 的能力差异也不只来自 UI。[`internal/handler/deployment_capabilities.go`](../../internal/handler/deployment_capabilities.go) 从已注册的后端 Handler 构造 `/system/capabilities` 快照；当 edition 为 Lite 时，组织能力会明确标成 `not_supported_in_lite`。前端应据此隐藏不可用入口，但真正的边界仍是后端不注册或拒绝相应 Route。

## 标准部署：把协调责任交给可替换服务

标准 Docker Compose 的入口是 [`docker-compose.yml`](../../docker-compose.yml)。它把 UI、App、PostgreSQL、Redis 和 DocReader 组合成一个可启动单元；Neo4j、MinIO、Qdrant 等服务则可按 profile 或配置启用。

```text
Frontend (Nginx)
       │ HTTP / SSE
       ▼
App ───────────────► PostgreSQL：业务数据、默认检索
 │  ├──────────────► Redis：任务、流、限流/协调
 │  ├──────────────► DocReader：复杂文档解析
 │  ├──────────────► 文件卷或对象存储：原文件与派生产物
 │  └──────────────► 可选向量库 / 图数据库 / 外部模型
```

这里的关键不是服务数量，而是依赖倒置：App 通过环境变量和配置选择 Driver，而业务层面对的是数据库、Retriever、Storage、Stream、Task Enqueuer 等抽象。比如 Compose 默认 `DB_DRIVER=postgres`、`RETRIEVE_DRIVER=postgres`，同时保留 `sqlite`、Elasticsearch/OpenSearch、Qdrant、Milvus 等配置入口；对象存储也可以从本地目录切换为 MinIO、S3、COS 等。

可替换不表示可以任意拼装。每次更换基础设施都要重新验证至少四件事：

1. **身份与命名空间**：一个 tenant、KB、文件和 Chunk 的稳定 ID 能否在新后端保持一致；
2. **语义**：检索过滤、删除、事务、一致性、分页和排序是否仍满足上层假设；
3. **故障模型**：超时、部分成功、幂等重试、备份与恢复的语义是否变化；
4. **运行边界**：网络、TLS、Secret、权限和成本归属是否同样可观测。

例如把本地文件改为对象存储并不是只换 `STORAGE_TYPE`：解析服务、App 的上传/下载路径和所有副本都必须访问同一 Bucket；删除、访问控制和预签名 URL 还要与第 26 章的租户边界对齐。

## 为什么 Redis 在标准版中不只是缓存

在这套架构中 Redis 承担流式事件、Asynq 队列、跨进程协调及部分限流/状态用途。将它简单当成“可以随时清空的缓存”会导致两类事故：

- 重启或故障转移后，浏览器无法回放未完成会话，后台 Worker 也丢失可消费工作；
- 多实例看见不同的运行状态，取消、并发控制和任务检查出现竞争。

不过 Redis 也不是业务真相的唯一来源。业务数据库仍应保存消息、文档处理状态和最终结果；队列是执行协调，Stream 是交互事件。第 22、23 章讨论的“流回放不等于计算恢复”“任务可重试不等于业务一定幂等”，在部署选择时仍然成立。

一个实用判断是：如果一个 Redis 键消失，系统应能否由数据库事实重建，或者至少能否把对应业务状态安全地收敛为失败。不能回答这个问题，就不应贸然把该键当作临时缓存。

## 容器编排没有自动带来高可用

[`helm/`](../../helm) 将标准服务转换为 Deployment、Service、Secret、PVC 和 Ingress。它解决了声明、调度和滚动发布，却不会自动把单机存储变成共享存储。

最容易被忽略的是 App 文件卷。Helm 默认的 `data-files` PVC 是 `ReadWriteOnce`。[`helm/README.md`](../../helm/README.md) 明确指出：RWO 允许同一节点上的若干 Pod 挂载，却不提供跨节点共享可写文件系统。若一个副本写入文件而另一个副本接到解析或下载请求，后者未必能看到它。

因此部署策略必须随存储能力变化：

```text
单 App + RWO 本地卷
  → 使用 Recreate 升级
  → 旧 Pod 退出、卷释放、新 Pod 启动
  → 可用性下降，但不会双挂载

多 App + 共享 RWX 卷或对象存储
  → 所有副本看到同一文件集合
  → 才可考虑 RollingUpdate 和横向扩容
  → 仍需分别验证数据库、Redis、DocReader 的容量与 HA
```

这也说明 `replicaCount: 3` 不是 HA 的证明。至少还要逐项检查：数据库是否有备份和故障转移，Redis 是否有持久化与高可用方案，文件是否共享，Ingress 是否支持长 SSE，Worker 是否有足够的资源隔离，以及模型供应商是否允许并发放大。

## 选择部署形态的决策表

| 场景 | 首选 | 不能忽略的代价 |
| --- | --- | --- |
| 个人知识库、演示、离线优先 | Lite/桌面 | 进程重启会中断内存流与执行中的任务；不提供多空间协作 |
| 小团队私有化、单机稳定运行 | Docker Compose 标准版 | 要维护数据卷、数据库、Redis、备份、版本升级与公网边界 |
| 多团队、受控入口、弹性资源 | Kubernetes + 外部/高可用基础设施 | 需要真正的共享存储、Secret/证书、可观测性、容量和发布策略 |
| 只想增加文档处理吞吐 | 先拆解 DocReader/Worker 瓶颈 | App 副本增加无法修复存储不共享或模型限流 |

不要把 Lite 当作生产标准版的“廉价预发布”，也不要把 K8s 当作无条件更高级的 Compose。前者优化的是局部性和低操作成本，后者优化的是独立伸缩、故障隔离和标准化运维；目标不同，复杂度的回报也不同。

## 发布、升级与回滚应围绕数据契约

镜像是可替换的，数据格式和外部副作用却未必可逆。一次可靠升级至少包括：

1. 记录当前镜像、配置版本、数据库迁移版本和外部 Driver 版本；
2. 备份数据库与文件/对象存储，并验证恢复，而不只验证备份任务成功；
3. 先检查 migration、索引重建、队列中旧任务和新增配置的兼容性；
4. 用健康检查确认 App 已连接到正确的依赖，而不是只确认 HTTP 端口可开；
5. 在灰度或维护窗口内观测登录、上传、检索、流式问答和后台解析；
6. 明确回滚点：代码可以回滚时，已执行的数据迁移、已发出的同步或已写入的外部对象怎么办。

Compose 的 `app` 健康检查和 Helm 的 liveness/readiness probe 都是必要信号，但不等于端到端可用。一个 `/health` 返回 200 的 Pod 仍可能连错 Bucket、无法调用模型、没有 Worker 消费队列，或者由于错误的 Ingress 缓冲使 SSE 表现为“卡住”。

3. [`internal/router/sync_task.go`](../../internal/router/sync_task.go)：理解 `SyncTaskExecutor` 怎样保持部分任务语义，以及为何它不具备跨进程持久性。
4. [`internal/container/container.go`](../../internal/container/container.go)：从 `initRedisClient` 和 Lite 注册路径观察依赖如何随 Redis 是否存在切换。
5. [`internal/handler/deployment_capabilities.go`](../../internal/handler/deployment_capabilities.go) 与 [`frontend/src/config/deploymentCapabilities.ts`](../../frontend/src/config/deploymentCapabilities.ts)：理解功能可用性怎样由后端事实传到 UI。
6. [`docker-compose.yml`](../../docker-compose.yml)：把环境变量按“数据库、检索、存储、流/队列、安全、可选服务”分类阅读。
7. [`helm/values.yaml`](../../helm/values.yaml) 与 [`helm/templates/app.yaml`](../../helm/templates/app.yaml)：观察配置怎样成为 Pod 环境变量、Service 和探针。
8. [`helm/README.md`](../../helm/README.md) 与 [`helm/templates/pvc.yaml`](../../helm/templates/pvc.yaml)：最后审查 RWO/RWX、更新策略和多副本前提。

## 常见误区

### 误区一：Lite 的异步任务等于可靠队列

Lite 会异步执行任务，也尽量处理重试；但待执行工作主要在进程内，崩溃恢复语义与持久队列不同。

### 误区二：有 Docker Compose 就天然适合生产

Compose 可以稳定运行，但备份、Secret 管理、主机补丁、监控、TLS、存储容量和灾难恢复仍由部署者负责。

### 误区三：把 App 多开几个副本就是扩容

如果文件仍是各节点本地卷，或者流和任务仍是进程内状态，只会得到间歇性的跨副本错误。

### 误区四：Driver 可替换，所以后端行为必然相同

检索召回、过滤、事务、索引构建、权限和删除传播都有差异；替换应有迁移与回归测试计划。

### 误区五：Health Check 成功代表用户路径正常

探针通常只验证进程可服务。上传、解析、检索、模型流和断线回放需要独立的合成检查与 Trace。

### 误区六：把 Redis 当作唯一事实源

它应协调执行和交互状态；业务最终状态必须落在可恢复的持久事实中。

## 本章小结

- 部署选择的核心是状态的位置、共享范围和恢复语义，而不是容器数量。
- Lite 以单进程 SQLite、本地文件、内存 Stream 与进程内任务换取零外部依赖；适合本地和小规模单机，不承诺分布式恢复。
- 标准版把业务数据、流/队列、解析和文件等职责拆给可替换基础设施，因而也需要维护这些依赖的安全与可用性。
- Redis 在标准架构中承担队列、流和协调；它不应取代业务数据库这一事实源。
- Helm 声明了部署资源，却不会自动解决共享存储、HA 或升级期间的卷挂载冲突。
- RWO 本地卷适合单副本并常常需要 Recreate；多副本需要经验证的 RWX 或对象存储，以及完整的依赖容量设计。
- 升级与回滚应围绕数据、迁移、外部副作用和端到端用户路径，而不只围绕镜像标签。

### 可选实践

为一个“50 人团队、每天上传 500 份 PDF、需要公司 SSO、一天内允许 30 分钟维护窗口”的部署画状态表。分别写出数据库、文件、检索索引、队列、流、Secret 和模型调用要放在哪里；说明为什么不能直接采用 Lite，为什么单纯把 Helm 的 `app.replicaCount` 改成 3 也不够。最后设计一次升级演练：列出备份验证、迁移、灰度检查、回滚判据，以及任一 Worker 在升级中断时如何让文档状态收敛。
