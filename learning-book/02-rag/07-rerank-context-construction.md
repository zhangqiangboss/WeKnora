# 第 11 章　Rerank、合并和上下文构造

[返回全书目录](../README.md) · [上一篇：关键词、向量与混合检索](06-hybrid-retrieval.md) · [下一篇：RAG 的失败模式与评测](08-rag-evaluation.md)

## 本章要解决的问题

混合检索结束时，我们得到的仍然只是一份“可能相关的 Chunk 候选”。它还不是可以直接交给大模型的上下文。

候选列表往往同时存在这些问题：

- 粗召回排序不够精细；
- 多个候选表达同一件事，浪费上下文；
- 命中的子 Chunk 太短，离开父级标题后语义不完整；
- 相邻 Chunk 被人为切开，答案跨越边界；
- 同一文档的连续片段可以合并，但不能错误吞掉重复表格；
- FAQ、正文、图片说明和历史引用需要不同的组织方式；
- 模型生成引用时，必须能稳定映射回真实知识来源。

所以检索后还有一段很重要的“证据加工”链路：

```mermaid
flowchart LR
    A["混合检索候选"] --> B["Rerank 精排"]
    B --> C["相关性阈值"]
    C --> D["MMR 去冗余"]
    D --> E["父级解析与片段合并"]
    E --> F["相邻上下文扩展"]
    F --> G["最终去重与 Top-K"]
    G --> H["上下文序列化"]
    H --> I["引用注册与模型消息"]
```

这一章的核心不是记住算法名，而是理解：**召回解决“可能在哪里”，上下文构造解决“怎样把证据安全、完整、经济地交给模型”。**

## 从传统搜索结果到模型证据

传统 Web 搜索页可以把十条独立结果交给用户，让用户自己判断标题、来源和上下文。RAG 不一样：结果首先交给模型，模型会把这些文本作为生成依据。

这带来三个额外要求：

1. **相关性**：有限上下文应优先给真正回答问题的证据；
2. **完整性**：证据不能因为切块而丢失标题、限定条件或前后句；
3. **可追溯性**：最终答案中的引用必须回到原始文档和 Chunk。

可以把它类比为 Java 后端中的 DTO 组装，但差异很大：普通 DTO 主要做字段映射，RAG 上下文组装还要做排序、降噪、语义补全、预算分配和数据血缘维护。

## Rerank：重新阅读查询与候选

第一阶段检索要在大量数据中快速找候选，通常依赖向量距离、BM25 或它们的融合排名。Rerank 则让专门模型逐个判断“这个候选对当前查询究竟有多相关”。

典型输入是：

```text
query: 差旅住宿的报销上限是多少？

passages:
  1. 差旅申请审批流程……
  2. 一线城市住宿标准每晚不超过 600 元……
  3. 出差交通工具等级规定……
```

输出通常是候选的新分数或新顺序。Rerank 模型能联合阅读查询与文本，因而比独立生成向量后比较距离更精细，但它也更慢，成本随候选数量和文本长度增长。

因此成熟链路通常是：

```text
快速召回较多候选 → 对有限候选精排 → 只保留少量结果
```

Rerank 不能在全库中发现新 Chunk。正确答案如果没有进入候选集，精排无论多强都找不回来。

## WeKnora 怎样执行 Rerank

WeKnora 的 `CHUNK_RERANK` 插件入口位于 [`rerank.go`](../../internal/application/service/chat_pipeline/rerank.go)。它使用查询理解阶段得到的 `RewriteQuery`，并把候选加工成更完整的 passage 后交给 Rerank 模型。

主流程可以概括为：

1. 没有执行检索、没有候选或没有配置 Rerank 模型时跳过；
2. 获取 Rerank 模型并构造非空 passage；
3. 按配置阈值调用模型；
4. 对模型分、原检索分和来源权重计算组合分；
5. 可选地提高 FAQ 结果；
6. 使用 MMR 在相关性和多样性之间再筛一次；
7. 把结果写入 `RerankResult`，供后续合并使用。

当前组合分的形式是：

```text
composite = 0.6 × rerank_model_score
          + 0.3 × retrieval_base_score
          + 0.1 × source_weight
```

结果会被限制到 0～1。Web 来源当前使用略低的来源权重，知识库来源为完整权重。

这不是 Rerank 的通用公式，而是 WeKnora 当前的产品选择。它表达了一个值得学习的思想：**精排模型是最重要信号，但不必完全抹掉粗召回和来源可信度。** 权重是否适合，仍要通过自己的数据集校准。

## 分数不是正确概率

检索分、Rerank 分和组合分都不应直接解释为“答案有 82% 概率正确”。

原因包括：

- 不同模型的分数分布不同；
- 查询类型会改变分数范围；
- 短文本、长文本、FAQ 和正文可能天然分布不同；
- 分数只描述相关性，不描述内容是否真实、是否过期；
- Chunk 相关不等于最终答案一定正确。

阈值应从真实正负样本的分布中得到，而不是凭直觉选择一个小数。尤其要观察阈值变化对无答案问题、容易混淆的负例和长尾查询的影响。

## 失败时是报错、回退还是降级

Rerank 是外部模型能力，必须设计失败语义。WeKnora 当前区分了几种情况：

- 模型配置无法获取：返回错误，因为预期能力根本不存在；
- Rerank API 调用失败：保留原检索候选继续，避免整次问答不可用；
- 当前阈值过滤后没有结果：如果阈值高于 0.3，会把它降低到原值的 70%，但最低不低于 0.3，再尝试一次；
- 仍没有结果：只在头部候选达到最低安全分时保留一个回退结果；
- 最终没有可用证据：返回“未搜索到内容”语义，而不是伪造上下文。

这里体现的是可用性与精度之间的取舍。降阈值能减少“明明有答案却返回空”的情况，也可能把弱相关证据交给模型。因此应记录是否发生过降级，并单独评估降级请求的答案质量。

## MMR：不要把五份同义证据都交给模型

单纯按相关性取 Top-K，可能得到五个几乎相同的片段。它们都很相关，却没有提供更多信息。

Maximal Marginal Relevance（MMR）在选择下一个候选时，同时考虑：

```text
MMR(d) = λ × relevance(d, query)
       - (1 - λ) × max similarity(d, selected)
```

- `relevance` 越高，越值得选；
- 与已选结果越相似，惩罚越大；
- `λ` 越高越偏向相关性，越低越偏向多样性。

WeKnora 当前在组合打分后以 `λ=0.7` 应用 MMR，并使用简单分词后的 Jaccard 相似度估计冗余。它不追求复杂语义去重，而是用低成本规则避免上下文被近似文本占满。

MMR 也有风险：如果同一答案需要多个非常相似但各含一个关键限定条件的条款，去冗余过强会丢失证据。调参时不能只观察“结果看起来更丰富”，还要检查答案所需的证据组合是否完整。

## 合并不是字符串拼接

Rerank 后的结果仍受切块边界影响。WeKnora 的 [`merge.go`](../../internal/application/service/chat_pipeline/merge.go) 把合并实现为一条明确的重建流程：

1. 优先选择 Rerank 结果，没有时回退到搜索结果；
2. 按 ID 或内容签名去重；
3. 注入当前问题引用到的历史知识结果；
4. 把子 Chunk 解析到需要的父 Chunk；
5. 按知识来源和 Chunk 类型分组，合并连续正文；
6. 补齐 FAQ 的答案内容；
7. 对过短正文沿前后 Chunk 扩展；
8. 扩展后再次合并，并执行包含部分重叠的最终去重。

这段代码值得逐阶段阅读，因为它展示了 Chunk 数据结构为什么不仅需要 `Content`，还需要：

- `KnowledgeID`：判断是否来自同一知识；
- `ParentChunkID`：恢复层级语义；
- `PreChunkID` / `NextChunkID`：恢复局部连续性；
- `StartAt` / `EndAt`：判断位置重叠；
- `ChunkType`：区分正文、FAQ、图片等不同内容；
- `SubChunkID`：保留合并来源和引用血缘。

## 父子 Chunk：检索粒度和阅读粒度可以不同

小 Chunk 通常更容易精确命中，但交给模型时可能缺少标题和解释；大 Chunk 语义完整，却容易让 Embedding 表达变得模糊。

父子 Chunk 是一种折中：

```text
检索：使用较小子 Chunk 找到精确位置
构造上下文：回到较完整父 Chunk 给模型阅读
```

WeKnora 在合并阶段批量解析父级。图片结果还可能沿“图片 → 文本说明 → 父正文”的链路恢复上下文。

但父级替换会扩大文本，多个子 Chunk 也可能指向同一父级，所以随后必须再次去重并重新控制预算。否则召回十个子 Chunk，最后可能重复塞入十份相同父正文。

## 相邻扩展：修复人为边界

一句答案经常恰好跨越两个 Chunk：前一个片段包含条件，后一个片段包含结论。只交命中片段会造成断章取义。

WeKnora 的 [`merge_expand.go`](../../internal/application/service/chat_pipeline/merge_expand.go) 会对较短的文本结果沿 `PreChunkID` 和 `NextChunkID` 扩展：

- 只处理普通文本 Chunk；
- 只连接同一 Knowledge 中的邻居；
- 当前少于 350 个字符时尝试扩展；
- 合并内容最多约 850 个字符；
- 扩展后的内容标记为已重写，并记录邻居 ID。

这些数字是当前实现的工程参数，不是所有语料的最佳值。技术手册、合同条款、聊天记录和源代码对上下文长度的需求完全不同。

## 为什么位置坐标不能永远相信

按 `StartAt` 和 `EndAt` 可以精确判断相邻片段的重叠，避免重复字符。但 Chunk 内容可能经过人工编辑、清洗或重写，这时旧坐标已经过期。

[`merge_overlap.go`](../../internal/application/service/chat_pipeline/merge_overlap.go) 只在以下条件满足时信任位置：

- 内容版本没有修改；
- 内容没有被重写；
- 结束位置大于开始位置；
- 实际字符长度等于坐标区间长度。

不满足时会采用更保守的内容合并策略。这个细节避免了一类隐蔽错误：把表格、日志或重复条款中“看起来相同”的文本误判为重叠并删除。

通用经验是：**只要内容发生转换，就必须重新验证与原文坐标之间的数据血缘。**

## 最终 Top-K 要在合并之后

合并会改变候选数量和内容长度，因此最终截断必须发生在合并之后。WeKnora 的 [`filter_top_k.go`](../../internal/application/service/chat_pipeline/filter_top_k.go) 按下面的优先级取输入：

```text
MergeResult > RerankResult > SearchResult
```

然后确定性排序，再按 `RerankTopK` 截断。稳定的并列排序很重要：如果相同请求因为 Go `map` 遍历顺序而得到不同上下文，线上问题和离线评测都难以复现。

当前这一层主要按结果数量控制 Top-K。数量预算不等于 Token 预算：一个父 Chunk 可能比另一个长很多。生产系统若有大量长度差异明显的内容，还需要结合模型上下文窗口，为系统提示、历史消息、证据和输出分别预留 Token。

## 上下文不是一坨字符串

最终证据需要清晰边界，让模型知道每段内容属于哪个来源。WeKnora 在 [`into_chat_message.go`](../../internal/application/service/chat_pipeline/into_chat_message.go) 中构造模型输入：

- 生成文档标题、描述和元数据头部；
- 把普通证据放入带 ID 的 `<context>` 结构；
- 把 FAQ 标记为高优先级 `<source type="faq">`；
- FAQ 优先时仍可把普通文档作为补充证据；
- 对不支持视觉输入的 Chat 模型追加图片文本说明；
- 加入用户附件、当前问题和历史消息；
- 渲染查询、上下文和语言等 Prompt 占位符。

使用 XML 风格边界不要求模型真正执行 XML 解析。它的价值是明确分隔指令、问题和不可信知识内容，减少多个来源粘连。

仍需记住：检索文档是数据，不是系统指令。外部文档可能包含“忽略之前要求”之类文本，Prompt 和权限设计不能把它当成高权限命令。

## 引用是数据血缘，不是方括号装饰

如果让模型直接记住数据库 Chunk ID，它可能输出不存在的 ID，也可能在合并后引用到错误子片段。

WeKnora 的 [`references.go`](../../internal/application/service/chat_pipeline/references.go) 会为本次请求创建模型上下文注册表，把真实检索结果注册成请求内句柄，再把引用协议加入系统消息。模型看到的是稳定、有限的可引用对象；应用保留句柄到真实知识和 Web 结果的映射。

完整链路是：

```text
原始 Knowledge / Chunk
  → SearchResult
  → 合并后的 SubChunkID 血缘
  → 请求内模型句柄
  → 模型输出引用
  → 后端解析为 Reference
  → 前端展示来源
```

因此引用质量至少包含两个问题：

1. 模型说的结论是否真的被引用内容支持；
2. 引用句柄是否正确映射到了原始来源。

答案文字正确但引用错了，仍然是 RAG 失败。

## 一次错误回答应怎样定位

假设模型把“600 元上限”回答成“800 元”，按下面的证据链检查：

| 检查位置 | 要问的问题 | 可能责任层 |
|---|---|---|
| 粗召回 | 正确条款是否进入候选？ | 切块、Embedding、关键词、查询、过滤 |
| Rerank | 正确条款是否被降到 Top-K 外？ | passage 构造、模型、阈值、组合权重 |
| MMR | 是否被相似但不完整的证据替换？ | 去冗余参数 |
| 合并 | 标题、限定条件、父级或邻居是否丢失？ | 层级和位置血缘 |
| 最终上下文 | 正确证据是否真的进入模型消息？ | Top-K、Token 预算、模板 |
| 生成 | 上下文正确但模型仍答错？ | Prompt、冲突证据、模型能力 |
| 引用 | 文本正确但指向错误来源？ | 注册表、合并映射、输出解析 |

先找到正确证据最后出现在哪一步，再调整参数。直接换一个更大的 Chat 模型，通常无法修复已经在上游丢失的证据。

## 与 Java/Web 开发的对应

可以用熟悉的概念建立第一层对应，但不要把二者完全等同：

| AI/RAG 概念 | Java/Web 类比 | 关键差异 |
|---|---|---|
| Rerank | 搜索结果业务排序 | 排序来自概率模型，输入长度和分布会影响结果 |
| MMR | 列表去重与多样性策略 | 不是按主键去重，而是按内容相似性惩罚 |
| 父子 Chunk | 查询明细后聚合主记录 | 聚合会扩大 Token 成本并改变引用粒度 |
| 相邻扩展 | 根据游标加载前后记录 | 还要处理文本重叠、切块边界和内容版本 |
| Prompt 上下文 | 组装下游请求 DTO | 内容本身可能被模型解释为指令 |
| 引用注册表 | 请求内 ID 映射 | 还要约束生成模型只能引用合法句柄 |

## 推荐源码阅读顺序

1. [`rerank.go`](../../internal/application/service/chat_pipeline/rerank.go)：先看精排、降级、组合分和 MMR。
2. [`merge.go`](../../internal/application/service/chat_pipeline/merge.go)：看注释列出的完整合并阶段，再进入各辅助文件。
3. [`merge_expand.go`](../../internal/application/service/chat_pipeline/merge_expand.go)：观察前后邻居怎样补全短上下文。
4. [`merge_overlap.go`](../../internal/application/service/chat_pipeline/merge_overlap.go)：理解位置可信度和重叠去除。
5. [`filter_top_k.go`](../../internal/application/service/chat_pipeline/filter_top_k.go)：确认最终输入优先级和确定性截断。
6. [`into_chat_message.go`](../../internal/application/service/chat_pipeline/into_chat_message.go)：看证据怎样进入 Prompt。
7. [`references.go`](../../internal/application/service/chat_pipeline/references.go)：沿引用句柄追踪回真实来源。

第一次阅读只跟一条普通文本文档结果，不要同时追 FAQ、图片、Web 和历史引用的全部分支。理解主线后再逐个补充特殊类型。

## 常见误区

1. **Rerank 会弥补召回遗漏。** 它只能重排已有候选。
2. **Rerank 分就是正确概率。** 它主要表达模型内部的相对相关性。
3. **去重只需比较 Chunk ID。** 不同 Chunk 可能包含相同或高度重叠内容。
4. **父 Chunk 一定比子 Chunk好。** 父级更完整，也更贵、更可能混入无关信息。
5. **Top-K 就控制了上下文长度。** 相同 K 下文本长度可以相差数倍。
6. **合并就是拼接字符串。** 还涉及顺序、重叠、版本、层级和引用血缘。
7. **答案正确就说明引用正确。** 引用支持度和来源映射必须单独检查。

## 本章小结

- Rerank 用更精细的查询—候选联合判断提高最终 Precision，但不能找回漏召回内容。
- WeKnora 综合 Rerank 分、原检索分和来源权重，并对 API 失败和空结果设计了回退语义。
- MMR 在相关性和内容多样性之间取舍，避免上下文被近似候选占满。
- 合并阶段负责恢复父级、连续片段和短 Chunk 的邻居上下文，同时维护去重与来源血缘。
- 最终 Top-K 应在合并后执行，且生产系统还要考虑 Token 预算。
- 上下文要有清晰来源边界；引用要通过请求内注册表稳定映射到真实知识。
- 调试错误回答时，应追踪正确证据在哪个阶段消失，而不是只看最终模型输出。

### 可选实践

选一个会召回多份相似说明的查询，依次记录 `SearchResult`、`RerankResult`、`MergeResult` 和最终上下文。对每个阶段回答三个问题：正确证据还在吗、重复减少了吗、限定条件保留了吗。然后关闭 Rerank 或调整 Top-K，比较最终答案和引用变化。
