# 第 12 章　RAG 的失败模式与评测

[返回全书目录](../README.md) · [上一篇：Rerank、合并和上下文构造](07-rerank-context-construction.md)

## 本章要解决的问题

一个 RAG Demo 很容易让人产生错觉：准备几份文档，问几个熟悉的问题，模型给出流畅答案，于是系统“已经可用”。真正进入生产后，问题会迅速出现：

- 同义改写后找不到原来能找到的答案；
- 同名产品或相似条款被混淆；
- 正确证据召回了，Rerank 却把它过滤掉；
- 上下文中有答案，模型仍然答错或漏掉限定条件；
- 答案看似正确，引用却不支持结论；
- 知识库没有答案时，模型仍然自信作答；
- 质量提高了一点，但延迟和模型费用翻倍；
- 改了切块后某类问题变好，另一类问题悄悄退化。

如果没有评测体系，团队只能依赖“多问几次感觉不错”。RAG 的不确定性被藏在检索模型、生成模型和随机样本里，每次改动都可能成为无法解释的回归。

本章给出一套从失败定位到离线评测、线上观测的完整框架，并对照 WeKnora 当前实现说明已经具备什么、还可以补什么。

## RAG 不是一个分数，而是一条因果链

最终答案由多个阶段共同决定：

```mermaid
flowchart LR
    A["问题与检索范围"] --> B["解析和 Chunk"]
    B --> C["搜索与融合"]
    C --> D["Rerank"]
    D --> E["合并与上下文"]
    E --> F["模型生成"]
    F --> G["引用与展示"]
```

如果只给最终答案打一个“对/错”标签，无法知道改哪里。更有效的评测至少拆成四层：

1. **检索质量**：相关证据有没有被找到、排在哪里；
2. **上下文质量**：正确、完整、无冲突的证据有没有进入模型输入；
3. **生成质量**：答案是否正确、完整、忠于证据；
4. **系统质量**：延迟、成本、稳定性、权限和可观测性是否合格。

最终答案指标是业务结果，分阶段指标是诊断工具。两者缺一不可。

## 先建立失败分类，而不是先调参数

一次坏答案可以按“正确证据最后出现在哪里”分类：

| 症状 | 优先检查 | 常见原因 |
|---|---|---|
| 搜索结果中没有正确证据 | 入库与粗召回 | 解析失败、切块不当、Embedding 不匹配、关键词缺失、范围或权限错误 |
| 搜索有，Rerank 后没有 | 精排 | passage 构造、阈值过高、模型不适配、候选过长 |
| Rerank 有，最终上下文没有 | 合并与预算 | 去重误判、父级映射、Top-K、Token 截断 |
| 上下文正确，答案错误 | 生成 | Prompt 不清晰、证据冲突、模型能力不足、温度过高 |
| 答案正确，引用错误 | 引用链 | 合并血缘丢失、句柄映射或引用解析错误 |
| 无答案问题仍然作答 | 拒答链 | 阈值过低、回退过宽、Prompt 未要求依据证据 |
| 偶发正确、难以复现 | 全链路 | 非确定排序、模型采样、外部服务变化、缺少版本记录 |

这个表比“换更强模型试试”更有用，因为多数检索失败不会被 Chat 模型修复。

## 一份评测数据应该包含什么

最小 QA 样本不只是问题和答案。为了评测检索，还需要知道证据在哪里：

```text
question          用户问题
reference_answer  一个或多个参考答案
relevant_ids      相关文档或 passage ID
passages          对应证据文本
answerable        当前知识范围内是否可回答
metadata          业务类别、语言、难度、时间、权限等切片标签
```

WeKnora 当前 [`QAPair`](../../internal/types/dataset.go) 包含 `QID`、`Question`、`PIDs`、`Passages`、`AID` 和 `Answer`，可以同时支撑检索与生成的基础评测。

生产数据集还值得增加：

- 是否应该拒答；
- 可接受的多个答案表达；
- 必须出现和禁止出现的事实；
- 期望引用的知识或 Chunk；
- 适用时间和知识版本；
- 租户、角色或权限条件；
- 问题类别与失败标签。

评测集不是越大越好。先建立一组规模较小、证据经过人工核验的 Golden Dataset，再持续从线上失败中补充困难样本。

## 数据集必须覆盖负例和边界

如果数据集只有“知识库中明确有一段原文答案”的简单问题，所有参数都会被优化成尽量回答。真正危险的样本被遗漏了。

至少覆盖：

- **直接事实**：原文能直接回答；
- **语义改写**：问法与原文几乎没有相同词；
- **精确实体**：错误码、型号、日期、条款号；
- **多证据问题**：答案需要组合多个片段；
- **易混淆负例**：相似产品、旧版本、同名概念；
- **无答案问题**：主题相关但知识中没有结论；
- **过期与冲突**：多个版本给出不同规则；
- **权限边界**：存在答案但当前用户不能访问；
- **多轮省略**：依赖上一轮指代；
- **图片或表格**：答案不在普通正文里。

开发集用于调参数，测试集用于最后验证。反复查看测试集再调阈值，会让测试集也发生泄漏，得到过于乐观的结果。

## 检索指标：答案证据排在哪里

### Precision@K

```text
Precision@K = Top-K 中相关结果数 / K
```

它回答：交给下游的候选有多“干净”。Precision 低意味着上下文噪声多，但如果 K 很小，也可能错过答案。

### Recall@K

```text
Recall@K = Top-K 中找到的相关结果数 / 所有相关结果数
```

它回答：应该找到的证据找到了多少。粗召回阶段通常更关注 Recall，最终上下文则需要兼顾 Precision。

### MRR

Mean Reciprocal Rank 只关心第一个相关结果的位置：

```text
某问题得分 = 1 / 第一个相关结果的排名
MRR = 所有问题得分的平均值
```

第 1 名相关得 1，第 2 名相关得 0.5，第 10 名相关得 0.1。它适合“找到第一个正确证据就足够”的任务。

### MAP

Mean Average Precision 会综合多个相关结果出现的位置。一个问题需要多份证据时，它比 MRR 更有信息量。

### nDCG@K

Normalized Discounted Cumulative Gain 同时考虑相关性等级和排名位置，并对越靠后的结果给予越小权重。若标注能区分“直接回答”“部分相关”“仅主题相关”，nDCG 比二元相关指标更合适。

任何指标都必须明确 K 和标注粒度。`Recall@50` 很高并不说明最终 `Top-5` 上下文足够好；按文档标注相关，也不等于其中每个 Chunk 都能支持答案。

## 应当按阶段保存检索指标

理想情况下，同一次实验至少保留：

| 阶段 | 主要问题 | 关注指标 |
|---|---|---|
| 关键词召回 | 精确实体能否找到 | Recall@N、MRR |
| 向量召回 | 语义改写能否找到 | Recall@N、MRR |
| 融合结果 | 两路结果是否互补 | Recall@N、nDCG |
| Rerank 结果 | 正确证据是否前移 | nDCG@K、MRR、Precision@K |
| 最终上下文 | 模型实际看到了什么 | Context Recall、Context Precision、Token 数 |

如果只保存最后一份列表，无法判断一次提升来自召回还是精排，也无法发现 Rerank 把高 Recall 变成低 Recall 的退化。

## 生成质量不能只看文字重合

答案评测至少包含这些维度：

- **正确性**：事实和结论是否正确；
- **完整性**：问题要求的要点是否都回答；
- **忠实性 / Groundedness**：每个事实是否得到上下文支持；
- **引用正确性**：引用是否真的支持对应结论；
- **拒答准确性**：无证据时是否拒答，有证据时是否避免过度拒答；
- **指令遵循**：格式、语言、长度和安全要求是否满足；
- **可读性**：结构是否清晰，是否包含无关内容。

BLEU 和 ROUGE 通过 n-gram 或序列重合比较生成答案与参考答案，计算便宜、稳定，适合批量回归。但它们有明显限制：

- 正确的同义表达可能分数很低；
- 复制大量参考文本可能得高分，却没有直接回答问题；
- 无法判断事实是否被检索证据支持；
- 无法可靠识别数字、否定词和限定条件造成的关键错误。

所以词面指标适合做信号，不适合成为唯一质量门槛。

## 人工、规则和 LLM Judge 怎样组合

没有一种评测器可以包办全部质量判断。

### 确定性规则

适合判断结构和明确事实：JSON 是否合法、必需字段是否存在、数值是否匹配、引用 ID 是否有效、无答案样本是否包含拒答标记。

### 词面指标

适合低成本观察大批量回归趋势，但要结合具体语言和答案形式解释。

### LLM-as-a-Judge

可以按评分 Rubric 判断正确性、完整性和证据支持度，覆盖同义表达。代价是评审模型也会有偏差、位置偏好和版本漂移。

使用 Judge 时应：

- 给出问题、参考答案、检索证据和待评答案；
- 把每个维度拆开评分，并要求给出理由；
- 固定模型、Prompt 和参数版本；
- 用人工标注集校准 Judge；
- 对边界分和重要失败进行人工复核。

### 人工评审

最贵，但仍是建立 Golden Dataset、校准自动指标和审查高风险场景的基准。重点不是让人检查每次发布，而是用少量高质量人工判断校准自动化体系。

## WeKnora 当前怎样评测

[`evaluation.go`](../../internal/application/service/evaluation.go) 中的 Evaluation Service 会创建异步评测任务，加载数据集，将 QA pair 转成知识 passage，然后并行执行问答管线并汇总进度和指标。

[`metric_hook.go`](../../internal/application/service/metric_hook.go) 在每个问题上记录：

- QA pair；
- 搜索结果；
- Rerank 结果；
- 最终 Chat 响应。

计算检索指标时，当前实现优先使用 Rerank 结果；没有 Rerank 结果才回退到搜索结果。随后通过内容包含关系，把返回 Chunk 映射回数据集的 passage ID。

这有两个值得注意的实现约束：

1. Hook 捕获了搜索与 Rerank 两个阶段，但当前聚合输出是一套检索指标，不是两套并排的阶段指标；
2. 内容包含映射简单直接，但 Chunk 被改写、重叠合并或只有部分对应时，可能影响 ground truth 归因。

当前 [`MetricResult`](../../internal/types/evaluation.go) 输出：

- 检索：Precision、Recall、nDCG@3、nDCG@10、MRR、MAP；
- 生成：BLEU-1、BLEU-2、BLEU-4、ROUGE-1、ROUGE-2、ROUGE-L。

这是一个扎实的离线评测骨架：任务、数据集、管线 Hook、并行执行、进度和聚合指标已经连通。若用于生产质量门禁，下一步可以增加分阶段检索结果、忠实性、引用、拒答、延迟、Token 和成本指标。

评测接口入口见 [`evaluation.go`](../../internal/handler/evaluation.go)，路由与权限配置见 [`routes_infra.go`](../../internal/router/routes_infra.go)。

## 系统指标：质量不是免费的

一次改动可能把 Recall 提高 2%，同时把 P95 延迟和 Rerank 费用提高一倍。工程决策必须联合观察：

- 端到端成功率和错误率；
- 空检索率、降阈值率、Rerank 回退率；
- 首 Token 延迟和总延迟的 P50 / P95 / P99；
- 搜索、Rerank、首 Token 和完整生成的分阶段耗时；
- 输入 Token、输出 Token 和上下文 Token；
- 每次请求和每个成功答案的成本；
- 模型、向量库和解析服务的失败率；
- 用户中断、重试和负反馈率。

不要只平均。少量超长文档或跨多个知识库查询可能只影响尾延迟，却正是用户体验最差的请求。

## 离线评测与线上评测各自回答什么

### 离线评测

在固定数据集上运行，适合：

- 比较切块、Embedding、检索权重、阈值和 Prompt；
- 发布前执行回归；
- 定位具体失败样本；
- 重复实验和消融分析。

缺点是数据集可能落后于真实流量，也无法完全模拟用户行为。

### 线上观测

来自真实请求，适合：

- 观察长尾问题和真实分布；
- 监控延迟、成本、错误和回退；
- 收集点赞、点踩、改问、复制、放弃等行为信号；
- 使用小流量 A/B 测试比较策略。

用户点赞不等于事实正确，用户没有点踩也不代表没有问题。线上弱信号要与抽样人工审查和离线标注结合。

## 一次可靠实验怎样做

假设要比较两个 Rerank 阈值，可以按下面步骤：

1. 冻结数据集和知识版本；
2. 固定解析、Chunking、Embedding、Chat 模型和 Prompt；
3. 只改变 Rerank 阈值；
4. 保存每个问题的搜索、Rerank、上下文和答案；
5. 比较整体指标和分类切片；
6. 查看“旧版正确、新版错误”的回归样本；
7. 联合比较延迟、Token 和成本；
8. 记录配置与代码提交，保证可复现。

这就是消融实验：一次只改变一个主要变量，判断它真正贡献了什么。若同时更换 Embedding、切块和 Prompt，即使指标变好，也无法知道原因。

## 版本化是评测可信度的一部分

至少记录：

- 代码提交；
- 数据集版本和样本划分；
- 原始文档或知识库版本；
- Parser 与 Chunker 配置；
- Embedding、Rerank、Chat 模型及供应商版本；
- 检索 Top-N、阈值、融合权重和 Top-K；
- Prompt 模板；
- Judge 模型、Rubric 和参数；
- 运行时间、随机参数与基础设施环境。

模型服务可能在名称不变时更新后端实现。对严格回归测试，应尽可能使用可固定版本的模型，并保留中间产物，避免只保存一个最终平均分。

## 从一次坏答案到回归样本

线上失败最有价值的处理方式不是立刻手工修 Prompt，而是进入闭环：

```text
发现坏答案
  → 保存问题、范围、中间候选、上下文和答案
  → 标注失败阶段与正确证据
  → 加入回归数据集
  → 修复一个明确原因
  → 全量离线重跑
  → 检查整体提升与其他类别退化
  → 小流量上线观察
```

长期来看，真正构成团队壁垒的往往不是某个模型调用，而是不断积累的失败分类、Golden Dataset 和可复现实验记录。

## 与传统 Web 测试的对应

| 传统 Web 工程 | RAG 对应物 | 新增难点 |
|---|---|---|
| 单元测试 | 指标计算、切块规则、引用解析测试 | 文本存在多种正确表达 |
| 集成测试 | 固定模型和知识上的全链路 QA | 外部模型与检索存在波动 |
| 接口契约测试 | Tool、模型消息、流事件 Schema | 模型可能生成不合法结构 |
| 性能测试 | 检索、Rerank、生成延迟与 Token | 成本随内容长度和模型变化 |
| 回归用例库 | Golden QA Dataset | 还需标注证据和失败阶段 |
| 线上监控 | Trace、质量反馈、回退与成本 | 质量通常不能由单个实时数值表达 |

传统断言没有消失。能确定的部分仍应使用严格断言；只有语义正确性和开放表达才需要统计指标或模型评审。

## 常见误区

1. **最终答案对，就说明检索好。** 模型可能依靠参数记忆猜对，引用却没有证据。
2. **Recall 越高越好。** 无限制扩大候选会增加噪声、延迟和成本。
3. **BLEU/ROUGE 高就代表事实正确。** 它们主要测文字重合。
4. **LLM Judge 是客观裁判。** Judge 也需要版本化、校准和人工复核。
5. **平均分提高就可以上线。** 关键业务切片或无答案样本可能正在退化。
6. **线上点赞就是 ground truth。** 用户行为是弱信号，受表达风格和使用场景影响。
7. **调多个变量更快。** 结果无法归因，下一次回归也无法定位。
8. **评测集一次建好就结束。** 它应随着真实失败持续演进。

## 本章小结

- RAG 质量必须拆成检索、上下文、生成和系统四层，最终分数与诊断指标并用。
- Precision、Recall、MRR、MAP 和 nDCG 从不同角度描述相关证据是否被找到并排在前面。
- 生成质量除了文字相似，还要评估正确性、完整性、忠实性、引用和拒答。
- WeKnora 已把异步任务、QA 数据集、管线 Hook 和基础检索/生成指标连成评测骨架。
- 当前实现有 Rerank 时以其结果计算一套检索指标；分阶段对比和更丰富的生成指标是自然的扩展方向。
- 离线数据集负责可复现比较，线上观测负责真实分布和系统行为，二者不能互相替代。
- 每次实验应只改变一个主要变量，并版本化代码、数据、知识、模型、配置和 Prompt。
- 最有价值的质量闭环，是把每次真实失败转化成永不丢失的回归样本。

### 可选实践

从自己的业务想象中写 20 个问题：5 个直接事实、5 个语义改写、3 个精确实体、3 个多证据问题、4 个无答案或易混淆负例。先不跑代码，只为每个问题标注正确证据和预期行为。然后用它检查现有 RAG，记录正确证据分别在搜索、Rerank、最终上下文和答案哪个阶段消失。
