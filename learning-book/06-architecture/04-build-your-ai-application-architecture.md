# 第 31 章　从 WeKnora 提炼自己的 AI 应用架构

[返回全书目录](../README.md) · [上一篇：哪些设计值得学习，哪些复杂度不必照搬](03-what-to-learn-what-not-to-copy.md)

## 本章要解决的问题

读完一套大型源码，最终目标不是复刻它，而是能为自己的问题画出第一版正确的边界、演进路径和验证方法。本章把前面的 RAG、Agent、异步、可观测、安全和部署知识压缩为一套架构决策流程。

## 从用户结果倒推，而不是从模型倒推

先写一句可验收的话，例如：

> 用户上传一份制度文档后，可在两分钟内获得带段落引用的问答；权限外的人不能检索；失败可解释、可重试。

这句话已经隐含了六类能力：身份/授权、文件与解析、索引、检索与生成、异步状态、引用与观测。模型只是其中一个不确定组件，而不是系统中心。

## 一份最小但可演进的蓝图

```text
Client
  → API / Auth / Request ID
  → Application Service
      ├── Knowledge lifecycle：file → parse → chunk → index
      ├── Query lifecycle：authorize → retrieve → context → generate → cite
      ├── Model Port：chat / embedding / rerank
      ├── Storage & Repository Port
      └── Task Port：long-running work and retry
  → PostgreSQL + file storage + one model provider
```

第一版不必拥有所有 WeKnora 子系统，但应具备以下不可妥协的契约：

| 契约 | 最小实现 | 将来如何扩展 |
| --- | --- | --- |
| 资源身份 | 文档、Chunk、会话都有稳定 ID 与 owner | Tenant、共享、派生资源与审计 |
| 检索证据 | 每个回答保留 Chunk ID、来源和版本 | Rerank、父子 Chunk、多模态、图谱 |
| 模型调用 | 超时、重试边界、用量/延迟记录 | Provider Adapter、模型路由与预算 |
| 长任务 | 状态机、幂等键、失败原因 | Redis Queue、Worker Pool、DLQ |
| 授权 | 请求入口和对象读取都验证 owner/scope | Role、API Key、外部 Principal、审批 |
| 可观测性 | Request ID、结构化日志、业务状态 | Trace、Span、成本、质量评测 |

## 把两个生命周期分开设计

知识入库与在线回答有不同的延迟、失败和一致性要求：

```text
离线：上传 → 解析 → Chunk → Embedding → Index → Ready/Failed
在线：请求 → 授权 → 查询理解 → Retrieval → Context → LLM → 引用/事件
```

不要让上传 HTTP 请求同步等待 OCR 和 Embedding，也不要让在线问答悄悄依赖“索引可能还没完成”。用明确状态将二者连接：用户知道文档何时 Ready，在线查询可选择忽略 Processing 文档或给出可理解提示。

## 先定义失败和预算

每条外部调用都要回答：最大等待多久？是否可重试？是否幂等？失败向用户显示什么？记录什么证据？

对 AI 系统，还要定义总预算：上下文 Token、模型轮数、工具次数、并发、单次成本、队列等待和端到端截止时间。WeKnora 的 RAG Filter Top K、Agent `MaxIterations`、Worker 队列和模型并发治理说明：局部组件各自“合理”，组合后仍可能超出成本和延迟预算。

## 用一条垂直切片验证架构

不要先建完所有目录再等待第一次验证。以一条“上传 PDF → 等待 Ready → 提问 → 看到引用”的垂直切片为主线，依次验证：

1. 身份能否只看到自己的文档；
2. 文档失败是否有可理解状态和重试入口；
3. 检索结果是否能反查到原文；
4. Prompt 是否只包含预算内的证据；
5. 模型超时、空回答和断流能否正确收口；
6. 日志/Trace 能否回答“为什么这次慢、贵或答错”。

通过这条切片后再增加第二个模型、Rerank、外部数据源或 Agent。每次扩展都应先补一条失败测试和一项观测，而不是只补一个 Provider 下拉框。

## 用架构决策记录控制演进

以下 ADR 模板足够开始：

```text
决定：第一阶段使用 PostgreSQL pgvector 与本地文件存储。
背景：文档量 < 10 万、单租户、团队无专职向量库运维。
后果：检索和业务数据共库；需监控索引大小与查询延迟。
触发升级：P95 检索延迟连续两周超过目标，或出现多租户隔离/独立扩缩需求。
退出方案：以 Chunk ID 和 Embedding 版本重建到新 Retriever。
```

ADR 的价值不在格式，而在于把“为什么现在够用、何时不够用、如何退出”写成团队可复查的事实。

## 最后的设计检查表

- 每份数据是否有稳定身份、归属和删除语义？
- 每个异步步骤是否有状态、幂等键、取消/重试和最终失败出口？
- 每次模型/工具调用是否有超时、预算、审计和可观测关联 ID？
- 检索证据、回答和用户权限是否能互相追溯？
- 外部 URL、密钥和模型输出是否都按不可信输入处理？
- 当新增第二个模型、第二个租户或第二个 App 副本时，哪些状态会失效？
- 是否有恢复演练，而不仅是健康检查？

若这些问题有明确答案，你已经拥有了一套可演进的 AI 应用架构；之后的选型只是在该架构内替换部件。

## 本章小结

- 从可验收的用户结果倒推能力，而不是从模型或框架倒推系统。
- 第一版应保留资源身份、证据血缘、授权、长任务状态、预算和观测这些难以事后补齐的契约。
- 将知识入库和在线问答视为两个生命周期，以业务状态连接。
- 用垂直切片与失败测试验证架构，再按真实触发条件演进基础设施和能力。
- WeKnora 的最大价值是提供了一张复杂系统的边界地图；你的系统应按自身风险选择其中需要的路线。

### 可选实践

为一个你准备开发的 AI 功能写一页架构蓝图：用户结果、两条生命周期、资源 ID、权限规则、一个模型 Port、任务状态机、三项预算、五个关键观测字段和两条升级触发条件。然后用本书的章节作为检查清单，标记哪些能力现在实现、哪些明确延后。
