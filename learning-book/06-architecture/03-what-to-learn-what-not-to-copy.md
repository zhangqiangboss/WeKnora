# 第 30 章　哪些设计值得学习，哪些复杂度不必照搬

[返回全书目录](../README.md) · [上一篇：事件管线、插件和策略模式](02-event-pipeline-plugin-strategy.md)

## 本章要解决的问题

阅读成熟项目最危险的收获，是把它的所有部件当成“生产级 AI 应用的必选清单”。WeKnora 的复杂度来自多租户、协作、长文档、多模型、多存储、Agent、外部数据源和多部署形态；这些是它回答的问题，不是每个新项目的起跑线。

本章给出一个判断框架：先学习其**边界意识**，再按真实风险引入实现复杂度。

## 最值得学习的不是目录，而是几个不变量

### 1. 把不可靠操作放到显式边界之后

模型、网络、解析器、外部数据源、队列和对象存储都可能超时、返回部分结果或重复执行。WeKnora 没有假设它们可靠，而是通过 Model/Provider Adapter、Task Enqueuer、Stream Manager、Storage Resolver 和 Retriever Registry 将变化集中在边界处。

可迁移的原则是：业务用例依赖能力与语义，供应商协议、连接配置、认证和错误格式留在 Adapter。即使你的第一版只有一个 OpenAI 兼容模型和一个 PostgreSQL，也应至少避免把 HTTP 请求和业务规则散落进 Handler。

### 2. 用状态机而不是“异步成功/失败”描述长流程

文档处理、Wiki、同步和 Agent 都不是一个布尔结果。它们会排队、执行、部分完成、重试、取消、死信和恢复。第 23 章中的 Queue/Worker 与业务状态分离，是值得从第一天保留的思想：任务系统负责“怎么跑”，业务记录负责“现在对用户意味着什么”。

这不要求小项目一开始部署 Redis。Lite 的 `SyncTaskExecutor` 正是一个好例子：上层先依赖 `TaskEnqueuer`，单进程时用进程内实现，需求出现后再切到 Redis/Asynq；但要诚实承认重启恢复能力随实现变化。

### 3. 把身份、租户和对象 Scope 当作数据流

多租户安全最容易在“读取一条对象”“后台任务”“模型生成参数”这些小地方漏掉。WeKnora 把 Principal、Tenant、Role/Capability、资源归属和 Agent Scope 放入调用链与 Guard 中，而不是只在登录时校验一次。

即使是单租户产品，也值得把当前用户、资源归属和权限判断显式化。日后引入团队、共享链接、API Key 或后台 Worker 时，这会避免把安全规则重写在几十个入口中。

### 4. 以观测和恢复设计流式体验

流式输出并非“把 token 转发到浏览器”。Request ID、会话消息、事件缓冲、完成标记、取消和错误分类，决定用户断网、刷新和服务重启时看到什么。用业务状态解释结果、用 Trace 诊断时间线、用事件存储改善展示恢复，这些原则比选 SSE 还是 WebSocket 更长寿。

### 5. 在配置能力前做验证和运行时 Gate

向量库、对象存储、数据源、MCP、Sandbox 是用户可配置的能力，也都是安全与运维边界。WeKnora 对 Driver、Capability 和部署形态做显式解析；第 27 章的 `/system/capabilities` 说明前端可见性应由后端事实驱动。

对自己的系统而言，先区分“可配置”和“实际可用”，并在保存配置、真正执行、异步恢复三个时点做相应校验。

## 不应一开始照搬的复杂度

| 能力 | 何时值得引入 | 过早引入的代价 | 轻量起点 |
| --- | --- | --- | --- |
| 多向量数据库 Driver | 客户确有不同存储/合规需求 | 测试矩阵、语义差异和迁移成本 | PostgreSQL + 一个明确索引策略 |
| 多 Worker Pool 与 DLQ | 任务类型争抢资源、重试需要运维 | 队列拓扑、面板、容量治理 | 一个队列 + 幂等任务状态 |
| Graph RAG / Wiki | 关系查询或自动知识编织有明确价值 | 抽取质量、撤回、图数据库运维 | 优先把普通 RAG 的 Chunk/引用做准 |
| 动态 MCP/Skill/Sandbox | 需要第三方工具或代码执行 | Secret、SSRF、审批、隔离和审计 | 少量受控的只读内置工具 |
| 多租户组织共享 | 有真实团队协作与隔离需求 | 每个读写路径、任务和缓存都要 scoped | 单租户，但提前保留 owner 字段 |
| 多副本 Kubernetes | 有容量/可用性和运维团队 | 共享存储、Secret、发布、监控 | Compose + 备份和恢复演练 |

“先简单”不等于把边界写死。应保留可演进的接口和数据身份，但不要部署尚无失败模式支撑的组件。

## 一个增量演进路线

```text
阶段 1：单租户、单模型、单存储
  → 可引用 RAG、请求日志、显式超时、基础权限

阶段 2：可恢复的知识处理
  → 业务状态、幂等、后台任务、失败可见

阶段 3：协作与配置化
  → Tenant/Role、模型与存储配置、审计、配额

阶段 4：外部扩展和规模化
  → Connector/MCP、队列治理、共享基础设施、端到端观测
```

每跨一步前问四个问题：新风险是否真实发生？当前失败是否能被观测？数据是否可迁移/回滚？团队是否能运行新增依赖？四个答案中有两个是否定，通常还不该引入。

### 手工推演：用触发条件，而不是焦虑，决定是否上队列

一个单人产品每天处理几十份文档，允许用户点击“重新处理”，进程偶尔重启的损失也可接受。此时先保留 `TaskEnqueuer` 边界、文档状态和幂等键，但使用单进程执行器，往往比立即部署 Redis、多个 Worker Pool 和 DLQ 更可靠：团队真的能观察和修复它。

当证据变成“高峰期上传会阻塞在线问答”“重启后有处理中的文档永远不结束”“不同任务互相抢占资源”，升级触发条件就已满足。此时再引入持久队列，并把原来的状态机与幂等键原样保留；队列只改变执行与恢复方式，不替代业务事实。这种演进比一开始复制全部拓扑更容易验证和回滚。

## 用 WeKnora 的代码做“复杂度审计”

[`internal/container/container.go`](../../internal/container/container.go) 同时装配 Redis Asynq Client/Inspector 与 Lite 的同步执行器/Noop Inspector；这表明抽象应服务于部署差异，而不是为了接口数量。[`internal/stream/factory.go`](../../internal/stream/factory.go) 也让 memory 与 Redis Stream 的选择显式化。

[`internal/application/service/file/resource_catalog.go`](../../internal/application/service/file/resource_catalog.go) 用 Resource Catalog 包装物理文件服务，展示了另一个值得学习的复杂度：当文件会跨存储、共享、引用和删除时，稳定资源身份比“直接保存路径”更重要。若你的产品还没有这些需求，先把文件记录和授权做清楚即可，不必提前复制全部 Catalog 能力。

## 常见误区

### 误区一：成熟项目用了，所以我的 MVP 也必须用

复杂度应由风险和规模付费，而不是由架构焦虑付费。

### 误区二：不引入组件就不需要设计边界

可以不部署 Redis，却仍可让业务依赖 `TaskEnqueuer`；可以只用一个模型，却仍应隔离 Provider 协议。

### 误区三：抽象天然降低成本

抽象增加间接层、测试面和配置错误空间。只有存在两个以上真实变化方向时才值得维护。

### 误区四：以后重构总是很容易

身份、资源 ID、业务状态和审计事实最难补。优先为这些不可逆数据留下演进余地。

## 本章小结

- 借鉴 WeKnora 时，应复制边界、状态、授权、观测与恢复的思维，而非复制所有组件。
- 任务状态与执行机制分离、身份与 Scope 显式传播、供应商 Adapter 隔离，都是早期就有回报的设计。
- 多存储、多队列、Graph RAG、动态工具、多租户和 K8s 都应由明确需求和运维能力触发。
- 最好的“简单”是保留演进方向的最小实现，而不是把未来边界埋进 Handler 和 SQL 中。

### 可选实践

为你自己的 AI 项目列一张“当前风险—最小机制—升级触发条件”表。至少覆盖模型失败、文档处理、数据权限、流式连接、文件存储和部署。选择其中一个当前还不需要的 WeKnora 能力，写出你暂不引入它的具体证据与未来触发阈值。
