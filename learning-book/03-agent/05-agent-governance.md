# 第 17 章　Agent 的权限、超时与失败恢复

[返回全书目录](../README.md) · [上一篇：Skills、沙箱和执行边界](04-skills-sandbox-boundary.md) · [下一篇：文档解析、OCR 与版面理解](../04-multimodal/01-document-parsing-ocr-layout.md)

## 本章要解决的问题

到上一章为止，Agent 已经拥有内置 Tool、MCP、Skill 和沙箱。能力越完整，一个更现实的问题越突出：怎样保证它只做被允许的事，并且在模型、网络、工具或用户中断时可预测地停下来？

传统 Web 系统中的权限判断多发生在一次请求进入 Controller 或 Service 时。Agent 不同：一次用户请求会展开成若干轮模型调用和工具调用，工具参数由模型动态生成，结果还会改变下一轮决策。一次授权不能自然覆盖整条动态链路。

本章建立三个相互约束的治理面：

```text
权限：这一步能不能做
预算：这一步最多能消耗多少时间、轮次、Token 和外部资源
恢复：失败后应该重试、换路、降级、暂停还是终止
```

它们不是上线前补上的运维配置，而是 Agent 状态机本身的一部分。

## 模型只能提出动作，不能授予权限

模型生成的 Tool Call 是一个不可信提议。即使它完全符合 Tool Schema，也只能说明参数结构合法，不能说明：

- 当前用户可以调用这个工具；
- 当前 Agent 被配置为可使用这个工具；
- 参数中的文档、知识库或租户属于当前主体；
- 这个写操作已经得到审批；
- 当前运行环境真的具备文件、网络或 Shell 能力。

有效权限可以用一个交集来理解：

```text
有效能力
  = 已认证主体权限
  ∩ Agent 预设能力
  ∩ 本次请求收窄范围
  ∩ 运行时真实 Capability
  ∩ 对象级授权
  ∩ 必要的人类审批
```

任何一项为空，动作都不能执行。这里最重要的性质是：**运行时输入只能收窄权限，不能扩大权限。**

用户在问题里写“请忽略限制”，Skill 文档声称“我需要访问所有文件”，或者模型猜出另一个知识库 ID，都不能改变这组交集。

## 控制面与数据面必须同时设防

可以把 Agent 权限拆成两层。

### 控制面：哪些能力对模型可见

控制面决定向模型暴露哪些 Tool、MCP Server、Skill 和沙箱能力。WeKnora 会结合 Agent 配置中的白名单和运行时能力注册工具；每轮通过 `@Skill` 或 `@MCP` 选择的能力只会进一步收窄既有集合。

控制面的价值有两个：

1. 减少攻击面，模型根本看不到无关高风险能力；
2. 减少 Tool Selection 噪声，提高模型选对工具的概率。

但“工具没有出现在 Prompt 中”不是完整安全边界。注册表和执行层仍必须拒绝未授权调用，避免其他代码路径、历史消息或协议错误绕过模型可见性限制。

### 数据面：工具能操作哪些对象

数据面回答的是：工具虽然可以调用，但能读取或修改哪些真实记录。

以知识检索为例，模型可能看到 `d1`、`c2` 这样的短句柄，也可能直接生成某个文档 ID。这些都不是授权凭证。WeKnora 的 [`scope_authorization.go`](../../internal/agent/tools/scope_authorization.go) 会重新解析持久化对象，再用服务端掌握的 `SearchTargets` 校验知识库、文档、标签和 Chunk 范围；禁用的 Chunk 也会被拒绝。

这里体现了一条通用原则：

> 用服务端身份和持久化关系重新授权，不信任模型回传的对象标识与来源声明。

这与 Java 应用中的 `@PreAuthorize` 仍有区别。方法级注解通常只检查“能否调用方法”，Agent 工具还需要在方法内部执行对象级授权，例如 `document.tenantId == principal.tenantId`。

## WeKnora 怎样收窄每次 Agent 请求

[`session_agent_qa.go`](../../internal/application/service/session_agent_qa.go) 是观察请求级治理的入口。它在进入 Engine 前完成多项确定性工作：

- 解析 Agent 预设允许的 Tool、Skill 和 MCP；
- 将本次 `@Skill` 选择约束在预设白名单内；
- 将本次 `@MCP` 选择约束在预设服务内；
- 从服务端上下文解析检索租户和知识范围；
- 把附件分阶段送入当前远程沙箱会话；
- 为共享 Agent 应用单独的来源与只读策略。

因此，`@Skill` 的含义不是“临时安装并授权一个能力”，而是“从已经允许的能力里明确选中一个”。`@MCP` 也一样。

### 共享 Agent 的双重身份问题

共享 Agent 可能由另一个工作空间创建，却被当前用户使用。此时至少存在两个问题：

- 检索应该使用共享者配置的知识范围，还是当前调用者自己的知识范围？
- 写工具应该以谁的权限执行？

WeKnora 将共享 Agent 的检索来源绑定到共享 Agent 所属租户，同时可以通过 `SharedAgentReadOnly` 过滤 Wiki 等变更工具。这说明“可分享配置”与“可转移写权限”不是一回事。

更一般地说，共享 Agent 应显式区分：

```text
配置所有者：提供 Prompt、知识源和能力预设
调用主体：发起当前请求并承担交互身份
资源主体：真实数据属于谁
执行主体：外部工具最终以谁的凭证运行
```

如果四种身份被压缩成一个 `tenantId`，跨租户共享越丰富，越容易出现权限混淆。

## 审批不是一个确认弹窗

Human-in-the-loop 适用于发消息、删除、发布、支付、变更外部系统等高风险动作。一个可靠审批必须绑定：

- 当前租户与用户；
- 当前 Agent、会话和请求；
- 精确工具名；
- 已规范化或摘要后的关键参数；
- 审批失效时间；
- 单次或限定次数的使用范围。

若用户批准“向 A 发送草稿”，模型在恢复后把收件人改成 B，原审批不能继续有效。审批的是具体动作，不是抽象意图。

WeKnora 的 [`approval/gate.go`](../../internal/agent/approval/gate.go) 会暂停工具调用，等待批准或拒绝；决策与租户、用户绑定，并支持通过 Redis Pub/Sub 跨实例唤醒。当前默认审批等待上限为 10 分钟，可由配置覆盖；审批检查异常时默认关闭通道，而不是把异常当成批准。

这叫 **fail closed**：无法确认安全时拒绝执行。对只读低风险功能可以设计明确降级，但不能把审批服务故障解释为“默认允许”。

## 超时不是一个数字，而是一棵预算树

只给整个 HTTP 请求设置一个 30 分钟超时，不能治理 Agent。子步骤可能吞掉全部时间，用户也不知道卡在模型、审批还是工具。

一个更完整的预算树是：

```text
请求总预算
├── Agent 最大轮次
├── 每次 LLM 调用超时
├── 每次 Tool 调用超时
│   └── Tool 内部网络、进程或数据库超时
├── 审批等待超时
├── 上下文 Token 预算
└── 工具结果与最终输出大小预算
```

### 预算耗尽时应该发生什么

设 Agent 正在汇总三份合同：前两次读取已成功，第三次远程工具在 25 秒后仍未返回，而总请求只剩 3 秒。此时继续等待，往往会让用户失去已经获得的两份证据；直接宣称完整成功，又会误导用户。

更可预测的策略是：取消尚未完成的低优先级工作，禁止新的写操作，用已完成证据生成“部分结果”，并在最终状态中记录 `budget_exhausted`、未完成步骤和可重试条件。预算不是单纯防止超时，而是决定系统在资源不足时怎样诚实地降级。

父预算必须覆盖子预算：子步骤的有效截止时间应当是自身上限与父级剩余时间的较小值。

### WeKnora 当前的几组默认值

从当前源码可以看到几种不同层次的保护：

| 预算 | 当前默认/限制 | 目的 |
|---|---:|---|
| 单次 LLM 调用 | 120 秒 | 防止模型端无期限等待 |
| 普通 Tool 执行 | 60 秒 | 限制单次外部动作占用 |
| Shell Tool 包装超时 | 约 10 分钟 | 允许较长作业，又保证最终退出 |
| LLM 瞬时错误重试 | 最多 2 次 | 吸收限流、服务端和短暂网络故障 |
| Agent 轮次 | 由配置决定，另有 100 的硬上限 | 防止循环失控 |
| 审批等待 | 10 分钟 | 避免永久占用悬挂状态 |

这些数值是当前 WeKnora 的实现默认，不是所有项目都应照抄的行业标准。批量数据分析、低延迟客服和支付 Agent 需要完全不同的预算。

预算还应包含“钱”和“副作用”：

- 每次请求最大模型成本；
- 最大搜索次数和外部 API 次数；
- 最大文件下载量、CPU 和内存；
- 最大邮件收件人数或可变更记录数；
- 同一工具连续失败次数。

Agent 不只会消耗计算资源，也会消耗真实世界的操作额度。

## 失败分类决定恢复动作

“调用失败就重试三次”是危险的统一策略。首先要分类。

| 失败类型 | 例子 | 推荐动作 |
|---|---|---|
| 瞬时基础设施故障 | 429、503、短暂断连 | 有上限退避重试 |
| 业务失败 | 库存不足、查询无结果 | 作为 Observation 返回，让 Agent 换路或解释 |
| 参数错误 | Schema 合法但业务字段无效 | 返回可修正错误，最多允许有限纠正 |
| 权限或审批拒绝 | 越权、用户拒绝 | 立即停止该动作，不重试、不绕过 |
| 永久配置错误 | 模型不存在、凭证缺失 | 快速失败，提示运维或配置修复 |
| 用户取消 | 前端主动中断 | 传播取消，保留已产生的部分状态 |
| 结果过大 | 搜索或日志超出上下文 | 截断、摘要、分页或外置 |
| 副作用结果未知 | 写请求超时，不确定是否成功 | 先查状态或用幂等键，禁止盲重试 |

最需要警惕的是最后一类。创建工单请求超时，不代表工单没有创建；直接重试可能创建两张。支付、发信和发布操作也是如此。

### 幂等键与状态查询

高风险写工具应接受由应用生成的稳定幂等键，例如：

```text
idempotencyKey = hash(sessionId, requestId, toolCallId, normalizedArgs)
```

远端支持幂等键时，重复请求返回第一次结果；不支持时，工具应尽量提供 `get_status` 或按业务唯一键查询的补偿路径。

模型不应自行生成幂等键，因为重试时它可能生成不同值。幂等性属于执行层协议，不属于自然语言推理。

## WeKnora 的 LLM 重试与证据降级

[`think.go`](../../internal/agent/think.go) 的 `callLLMWithRetry` 会识别限流、5xx、超时、连接错误等瞬时特征，在有限次数内退避重试。重试仍失败时，如果前面已经取得工具结果，Engine 会尝试基于现有证据合成最终回答。

这个降级很有价值：

```text
完整成功：继续规划并完成任务
部分成功：不再调用新工具，用已有证据解释已完成和未完成部分
完全失败：返回分类后的错误
```

但并非所有失败都适合“尽量给一个答案”。用户明确取消时，不应又生成一段看似正常的替代回答；权限失败时，也不能用参数记忆猜测受保护数据。

## Tool 错误应成为结构化 Observation

工具可能返回三种不同语义：

1. 成功并有数据；
2. 成功执行但业务结果为空，例如没有命中；
3. 执行失败，例如超时或权限不足。

如果都压成一段字符串，模型很难判断应该改查询、换工具还是结束。理想的 Observation 至少包含：

```json
{
  "status": "error",
  "category": "permission_denied",
  "retryable": false,
  "message": "document is outside the allowed scope",
  "details": null
}
```

给模型的错误信息要可行动，但不能泄露内部路径、凭证、其他租户对象是否存在等敏感信息。详细堆栈进入日志和 Trace，模型只得到经过脱敏的分类。

## 上下文溢出也是一种运行时失败

Agent 每轮都会新增 assistant Tool Call、tool result 和下一步推理。即使每个工具都成功，最终也可能因为上下文膨胀而失败。

WeKnora 在 [`observe.go`](../../internal/agent/observe.go) 中同时处理当前轮工具结果和历史消息：

- 当前轮工具结果使用单独预算，约为最大上下文的 20%，并限制在 8K～32K Token；
- 截断时保留 assistant Tool Call 与 tool result 的配对关系；
- 历史超过阈值时使用 Memory Consolidator 总结；
- 总结失败时回退到简单压缩；
- 默认从历史中移除旧知识检索结果，要求重新检索可能变化的知识。

这里有两个很重要的工程认识。

第一，压缩不是无损序列化。摘要可能丢失数字、否定条件或来源，所以关键审批、执行结果和业务标识不应只存在于自然语言摘要里。

第二，动态知识应该重新检索。把几轮前的知识库结果永久留在上下文中，既浪费 Token，也可能使用已经禁用或更新的 Chunk。

## 历史恢复以持久化状态为准

[`agent_history.go`](../../internal/application/service/agent_history.go) 把数据库作为 Agent 历史的单一事实来源。恢复时只读取完整的用户—助手请求对，并重建：

- assistant 的 Tool Calls；
- 与调用 ID 对应的 tool 消息；
- 最终 assistant 内容；
- 图片、附件等规范化用户输入。

未完成的助手消息不会被当成一轮已完成历史。这避免服务重启后把半条流式响应误认为可靠上下文。

对 Java 开发者，可以把它理解为事件恢复与数据库快照之间的折中：不是重放所有内部对象，而是从规范化持久记录重建模型协议需要的消息。Redis 或内存缓存可以加速，但不能成为唯一事实来源。

## 取消必须沿调用链传播

用户点击“停止生成”后，取消信号应该穿过：

```text
HTTP/SSE → Agent Engine → LLM Stream → Tool Context → 外部网络/进程
```

如果中间某层创建了脱离父 Context 的后台任务，前端虽然停止显示，后端仍可能继续下载、发信或执行脚本。

取消后的正确处理通常是：

- 停止创建新的 Tool Call；
- 尽力取消正在进行的只读或可取消任务；
- 对已提交的外部写操作记录“结果未知”，而不是声称回滚成功；
- 持久化已确认完成的步骤和取消原因；
- 只发送一次终止/完成事件。

WeKnora Engine 使用 Context 检查取消，并用一次性完成事件避免多个退出分支重复收尾。必要的收尾持久化可以使用不受原取消信号立即打断的短 Context，但必须有独立短超时，不能借此继续业务执行。

## 从重试到恢复的四个层次

恢复不是重试的同义词，可以按影响范围分层：

### 1. 原地重试

同一步、同一参数、同一幂等键，仅用于可重试瞬时故障。

### 2. 路径切换

把结构化失败作为 Observation，让模型改查询、换只读工具，或向用户请求缺失输入。切换后的动作仍要重新授权。

### 3. 功能降级

不再调用新工具，使用已获得证据生成部分回答；或者从复杂解析切换为明确标注质量较低的纯文本路径。降级必须可见，不能伪装成完整成功。

### 4. 会话恢复

进程重启或长审批后，从持久化消息、工具调用记录、沙箱 Binding 和外部操作状态恢复。恢复点必须说明哪些步骤已确认提交，哪些步骤结果未知。

这与 Saga 的思想接近，但 Agent 的步骤不是预先固定的。补偿策略应由每个工具的确定性实现声明，不能让模型临时编造“撤销动作”。

## 熔断、隔离与背压

当某个模型或 MCP Server 持续失败时，逐请求重试会放大故障。生产系统还需要：

- **熔断**：连续失败超过阈值后短期拒绝新调用；
- **并发隔离**：不同租户、模型和高成本工具使用独立并发池；
- **背压**：队列过长时拒绝、排队或降级，而不是无限创建 Goroutine；
- **限流**：按租户、用户、Agent 和供应商分别计量；
- **重试预算**：限制全局重试流量，避免重试风暴。

超时只终止单次慢调用，熔断处理持续性故障，背压处理系统过载，三者不能互相替代。

## 可观测性必须回答“为什么执行了这一步”

普通 API 日志经常只记录 URL、状态码和耗时。Agent 审计至少还需要：

- 租户、用户、Agent、会话和请求 ID；
- 当前轮次与状态；
- 模型版本、Prompt/Tool 集版本；
- 模型提出的工具名和脱敏参数摘要；
- 授权范围与审批决策；
- 工具结果分类、耗时和重试次数；
- Token、成本和上下文压缩事件；
- 取消、降级、最终终止原因；
- 有副作用操作的幂等键和外部结果 ID。

“模型决定调用了 send_email”不是充分审计理由。系统还要记录 Tool 为什么对该 Agent 可见、哪个确定性策略允许执行、谁批准了哪些参数。

## 一套可测试的 Agent 治理矩阵

权限和恢复不能只靠人工试用。至少应覆盖：

| 测试维度 | 关键用例 |
|---|---|
| Tool 白名单 | 模型伪造未注册工具名时被拒绝 |
| 对象级授权 | 合法格式的跨租户 ID 被拒绝且不泄露对象存在性 |
| 请求收窄 | `@Skill`、`@MCP` 不能扩大 Agent 预设 |
| 共享 Agent | 可读取约定来源，但写工具被过滤 |
| 审批 | 批准参数被修改后必须重新审批；超时与拒绝均 fail closed |
| 超时 | LLM、Tool、审批、总请求分别触发正确分类 |
| 重试 | 429 可重试，权限错误不重试，写超时不盲重试 |
| 取消 | 停止后不产生新工具动作，只发送一次终止事件 |
| 上下文 | 超大工具结果被裁剪且 Tool Call 配对仍合法 |
| 恢复 | 半完成消息不进入历史，已完成外部动作不重复提交 |

这些测试很多不需要真实大模型。可以用脚本化 Fake Model 输出指定 Tool Call，再断言执行层行为。治理逻辑越确定性，越容易稳定回归。

## WeKnora 当前实现给我们的启发

值得学习的设计包括：

- 请求级 `@Skill` / `@MCP` 只做能力收窄；
- 模型句柄之外还有服务端对象级范围校验；
- 共享 Agent 单独处理来源租户和只读能力；
- Tool、LLM、审批和轮次各自有预算；
- 瞬时模型失败有限重试，已有证据可用于降级收尾；
- 上下文裁剪保留模型协议配对，动态知识默认重新检索；
- 数据库历史是恢复事实源，未完成轮次不冒充完成；
- 审批异常默认拒绝。

同时也应看清“当前选择”和“可继续演进方向”的区别。例如，使用错误字符串识别 429、5xx 和超时很实用，但供应商增多后最好逐步收敛为带错误码、重试性和副作用状态的类型化错误。若产品要求严格的端到端 SLA，也应在各子超时之外显式定义总请求截止时间和剩余预算传播。

## 与传统 Java/Web 系统的对应

| Agent 治理概念 | Java/Web 对应 | 新增难点 |
|---|---|---|
| Tool 白名单 | API 路由/方法授权 | 方法集合按 Agent 和每轮动态变化 |
| 对象级授权 | Service 内数据权限 | 参数由模型生成，不能信任来源 |
| 审批 Gate | 工作流人工节点 | 暂停后要跨实例、跨时间恢复 |
| Context 取消 | HTTP 请求取消 | 还要传播到模型流、工具和进程 |
| 最大轮次 | 循环/工作流步数上限 | 下一步由模型动态决定 |
| Observation 错误 | 领域异常 DTO | 同时要供模型决策且避免泄密 |
| 历史重建 | 从数据库恢复会话 | 必须保持 Tool Call 协议配对 |
| 幂等工具 | 幂等 REST / 消息消费 | 模型可能重复规划同一副作用 |

可以把生产 Agent 看成“由概率规划器驱动的工作流引擎”。规划可以灵活，权限、预算、提交和恢复必须确定。

## 推荐源码阅读顺序

1. [`const.go`](../../internal/agent/const.go)：先看 LLM、Tool、重试和重复响应的默认预算。
2. [`engine.go`](../../internal/agent/engine.go)：看循环上限、取消、状态和最终事件。
3. [`think.go`](../../internal/agent/think.go)：跟踪模型超时、瞬时错误重试与已有证据降级。
4. [`observe.go`](../../internal/agent/observe.go)：看工具结果预算、历史压缩和终止判断。
5. [`session_agent_qa.go`](../../internal/application/service/session_agent_qa.go)：看请求如何收窄 Skill、MCP、知识范围和共享 Agent 权限。
6. [`scope_authorization.go`](../../internal/agent/tools/scope_authorization.go)：重点看模型句柄怎样重新映射并接受对象级授权。
7. [`approval/gate.go`](../../internal/agent/approval/gate.go)：理解审批暂停、主体绑定、超时和跨实例通知。
8. [`agent_history.go`](../../internal/application/service/agent_history.go)：最后看完整轮次怎样从数据库重建。

第一次阅读时，构造“读一个允许文档”和“读一个范围外文档”两条路径，对比 Tool Schema 完全相同而执行结果不同的原因。然后再加入一个需要审批的写工具和一次用户取消。

## 常见误区

1. **Tool 出现在 Prompt 中就代表可以执行。** 可见性只是控制面，执行时仍需对象级授权。
2. **Tool Schema 已经校验了安全性。** Schema 只约束结构，不证明主体、对象和业务规则合法。
3. **用户点名一个 Skill 就授予了 Skill 权限。** 点名只能从预设白名单中收窄选择。
4. **只读工具没有风险。** 它仍可能跨租户泄露、访问内网、消耗大量费用或形成侧信道。
5. **所有错误都重试三次。** 权限拒绝、配置错误和非幂等副作用不能盲重试。
6. **请求超时就说明写操作失败。** 远端可能已经提交，必须使用幂等键或状态查询确认。
7. **压缩历史等同于保存历史。** 摘要是有损的，关键状态应结构化持久化。
8. **取消只需要让前端停止渲染。** 后端模型流、工具、进程和外部动作仍可能继续。
9. **审批过一次以后同类动作都可执行。** 审批应绑定具体参数、主体和有效期。
10. **共享 Agent 等于共享所有者权限。** 分享配置、知识与写权限必须分别建模。

## 本章小结

- 模型只提出 Tool Call，确定性应用才拥有授权和执行权。
- 有效能力是主体权限、Agent 预设、请求范围、运行时 Capability、对象级授权和审批的交集。
- 控制面限制模型看见什么，数据面限制工具能操作什么；两层都要检查。
- `@Skill`、`@MCP` 和共享 Agent 场景必须遵守“只能收窄，不能扩权”。
- 超时应形成总请求、轮次、LLM、Tool、审批、Token 和资源额度组成的预算树。
- 失败要先分类，再选择重试、换路、降级、恢复或终止。
- 非幂等写操作结果未知时不能盲重试，幂等键应由执行层稳定生成。
- 上下文裁剪、历史重建和动态知识重检索是 Agent 恢复的一部分。
- 取消必须传播到整条调用链，收尾持久化不能借机继续业务动作。
- 可观测性要记录“为什么允许并执行”，而不只是模型调用了什么。

### 可选实践

选择一个“查询订单”和一个“取消订单”Tool，为它们写一张治理表：列出 Tool 白名单、对象级授权、审批条件、单步超时、是否可重试、幂等键、结果未知时的状态查询、取消语义和审计字段。再用 Fake Model 构造跨用户订单 ID、重复 Tool Call、审批后篡改参数和远端超时四个测试，不必接入真实 LLM。
