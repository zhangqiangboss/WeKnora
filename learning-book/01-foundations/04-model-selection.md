# 第 4 章　模型能力、成本、速度与选择

[返回全书目录](../README.md) · [上一篇：Token、上下文、消息与 Prompt](03-token-context-message-prompt.md) · [下一篇：一张图理解 RAG](../02-rag/01-rag-overview.md)

## 本章要解决的问题

“应该选哪个模型”不是一张排行榜能回答的问题。一个 AI 应用会同时使用 Chat、Embedding、Rerank、VLM、ASR 等不同能力，而同一类能力也要在质量、延迟、成本、隐私和可运维性之间取舍。

本章建立一个工程化选择框架，而不是推荐某个随时间变化的具体型号。

## 先按任务类型分模型

WeKnora 将模型显式区分为：

- `KnowledgeQA`：聊天、总结、查询理解和生成；
- `Embedding`：文本向量化；
- `Rerank`：候选精排；
- `VLLM`：视觉语言理解；
- `ASR`：语音识别。

定义见 [`internal/types/model.go`](../../internal/types/model.go#L14)。

这种分类比“统一接一个最强大模型”更符合工程现实。RAG 的批量入库需要高吞吐 Embedding，在线回答需要低首字延迟 Chat，精排需要查询—文档相关性模型，图片处理则需要视觉能力。

## 六个选择维度

### 1. 任务质量

不要只看通用榜单，应在自己的任务上测试：

- 中文和行业术语；
- 长上下文证据利用；
- 引用约束；
- 工具调用准确性；
- JSON/结构化输出；
- 无答案和冲突证据处理。

Embedding 则关注检索召回率，Rerank 关注排序质量，而不是语言生成观感。

### 2. 延迟

至少拆成：

- 请求排队时间；
- 首 Token 延迟；
- 输出 Token 速度；
- 完整请求耗时。

流式回答主要改善感知延迟，不能缩短全部计算。RAG 还要叠加查询改写、Embedding、搜索和 Rerank，因此应按阶段观测。

### 3. 成本

远程模型成本通常包含输入和输出 Token；Embedding 常按输入量计费；Rerank 按查询与候选文本量计费。还应计入：

- 重试和失败调用；
- 查询改写、标题生成等辅助调用；
- 文档重新索引；
- 向量和对象存储；
- 本地模型的 GPU、内存和运维。

本地模型不是零成本，只是把按次账单转为固定资源和运维成本。

### 4. 上下文和输出能力

需要核对：

- 最大上下文；
- 最大输出；
- 是否支持流式；
- 是否支持工具调用、并行工具和结构化输出；
- 是否支持图片；
- 是否要求回传推理内容；
- Tokenizer 和消息协议兼容性。

“上下文很大”也不代表对长文证据的利用一定更好，仍需用任务评测。

### 5. 数据与合规

企业知识可能包含客户资料、合同和内部代码。选择远程或本地模型时需回答：

- 数据传到哪个地区和供应商？
- 是否用于训练或保留日志？
- API Key 如何存储和轮换？
- 是否需要专线、私有部署或审计？
- 多租户凭据和模型配置怎样隔离？

WeKnora 的模型参数在持久化时对 API Key 和 AppSecret 进行 AES-GCM 加密，见 [`ModelParameters.Value`](../../internal/types/model.go#L154)。这解决静态凭据保护，但不替代供应商合规评估。

### 6. 可运维性

需要考虑：

- 额度与限流是否稳定；
- 是否支持健康测试；
- 模型版本是否可固定；
- 是否有兼容 API 和降级模型；
- 本地部署是否有足够显存与并发；
- 出错时能否区分配置、网络、额度和协议问题。

## 不要用一个模型承担所有阶段

一个常见的成本优化是任务分层：

- 小模型做查询改写、分类和标题；
- Embedding 模型专门负责索引和查询向量；
- Rerank 模型只处理候选集；
- 更强 Chat 模型负责最终回答或复杂 Agent；
- VLM 仅在存在图片时使用。

但模型越多，配置、故障和评测矩阵越复杂。小规模系统可以先使用少量稳定模型，效果或成本出现瓶颈后再拆分。

## Chat 模型怎样选择

按顺序问：

1. 是否支持需要的语言、上下文、流式和工具能力？
2. 在固定评测集上是否达到最低正确率？
3. P50/P95 首字延迟和总延迟是否可接受？
4. 单次请求与月度成本是否可控？
5. 数据政策是否允许？
6. 失败时有没有降级路径？

RAG 场景还应单独测试“基于证据回答”和“证据不足时拒答”，而不是只测开放聊天。

## Embedding 模型怎样选择

关键维度包括：

- 领域和语言召回质量；
- 向量维度与存储成本；
- 最大输入 Token；
- 批处理能力和吞吐；
- 查询与文档是否需要不同前缀；
- 模型升级时的重建成本。

Embedding 模型一旦改变，旧向量和新查询向量通常不在同一空间，需要重新索引全部文档。它比替换 Chat 模型具有更高迁移成本。

WeKnora 在模型参数中保存维度和截断限制，见 [`EmbeddingParameters`](../../internal/types/model.go#L58)。知识库搜索还会检查跨库 Embedding 一致性，避免比较不同空间的分数。

## Rerank 模型怎样选择

Rerank 的输入量取决于粗召回候选数量。应评估：

- 正确片段能否从 Top-N 提升到最终 Top-K；
- 中英文和长候选表现；
- 单次支持多少文档；
- 候选批处理的延迟与费用；
- 不可用时是否退化为原召回排序。

如果粗召回经常漏掉正确片段，先优化 Chunking 和召回，不要指望 Rerank 修复不存在的候选。

## 本地模型与远程模型

| 维度 | 本地模型 | 远程 API |
|---|---|---|
| 初始使用 | 需要部署和资源 | 配置凭据即可 |
| 弹性 | 受本机/GPU 限制 | 通常更容易扩展，但有限流 |
| 数据控制 | 较强 | 依赖供应商政策 |
| 成本形态 | 固定资源和运维 | 按量或套餐 |
| 模型更新 | 自己管理 | 供应商管理，可能发生漂移 |
| 故障责任 | 自己排查全栈 | 还依赖外部服务状态 |

WeKnora 的 Chat 工厂按 `local` 与 `remote` 分流，本地使用 Ollama，远程再按 Provider 适配，见 [`NewChat`](../../internal/models/chat/chat.go#L142)。

## WeKnora 的模型配置层

模型实体保存：

- 类型、来源、Provider 和模型名；
- Base URL 和凭据；
- Embedding 维度及截断设置；
- 是否支持视觉；
- 后台调用并发上限；
- 供应商扩展参数和自定义请求头；
- 状态、默认模型和内置模型属性。

模型 Service 根据 ID 读取配置，再创建对应 `Chat`、`Embedder`、`Reranker` 或 `VLM` 接口实例。入口见 [`internal/application/service/model.go`](../../internal/application/service/model.go#L412)。

内置模型还可通过 YAML 声明式下发，说明见 [`docs/BUILTIN_MODELS.md`](../../docs/BUILTIN_MODELS.md)。

## 并发不是单纯把数字调大

文档入库会批量调用 Embedding，多模态和 Wiki 也会产生后台模型任务。如果所有 Worker 同时打满一个供应商，可能触发限流并导致重试风暴。

WeKnora 为部分模型配置 `MaxConcurrency`，并通过包装器对后台调用做并发治理。交互请求与后台吞吐的优先级也应区分。

调并发时应同时观察：

- 供应商速率限制；
- 单请求批量大小；
- Worker 数；
- P95 延迟；
- 429/超时率；
- 队列积压。

吞吐最大值通常出现在“并发足够但尚未造成上游拥塞”的位置，而不是无限增加。

## 建立自己的模型评测卡

每个候选模型至少记录：

| 类别 | 指标示例 |
|---|---|
| 质量 | 正确率、引用支持率、召回率、工具成功率 |
| 延迟 | P50/P95 首 Token、总耗时 |
| 成本 | 每问题输入/输出 Token、每千文档入库成本 |
| 稳定性 | 超时、429、格式错误率 |
| 能力 | 上下文、流式、工具、视觉、结构化输出 |
| 治理 | 数据区域、日志策略、版本固定、凭据方式 |

只有在同一数据集、同一 Prompt 和相近参数下比较，结论才有意义。

## 常见误区

1. **只按参数量或榜单选模型。** 应按实际任务和运行约束选择。
2. **本地模型等于免费。** 资源、能耗、部署和运维都有成本。
3. **替换 Embedding 像替换 Chat 一样简单。** 通常需要全量重建索引。
4. **最大上下文就是有效上下文。** 长证据利用能力需要实测。
5. **并发越高吞吐越大。** 上游限流会让系统进入拥塞和重试放大。

## 本章小结

- 先按 Chat、Embedding、Rerank、VLM、ASR 区分任务，再选择模型。
- 模型选择是质量、延迟、成本、能力、合规和运维的多目标决策。
- Embedding 更换通常意味着重建索引，迁移成本高于 Chat 模型。
- 模型分层能优化成本，但也增加配置与故障矩阵。
- 本地和远程只是不同成本与治理形态，没有绝对优胜者。
- 模型结论必须来自固定数据集和端到端指标。

### 可选实践

为你计划使用的 Chat、Embedding 和 Rerank 各做一张空白评测卡，只定义要记录的指标，不必立刻选择具体模型。
